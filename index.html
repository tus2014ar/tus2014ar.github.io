The pragmatic builder

Everything I build is grounded in a production mindset.

"Understanding existing systems deeply before changing them, designing for the next person who has to maintain my work, and communicating technical findings in a way non-technical stakeholders can act on." That’s the standard I actually build to.

01

Never breaks the upstream job

Every data quality and cost pipeline I've shipped runs as a soft-fail observer: a failing check writes a finding row, it never raises and kills the parent job. A DQ failure is a data observation, not a pipeline outage.

→ see it in Cost Analytics 02

Idempotent by design

Every gold table load pairs with a post-write uniqueness check that runs on every execution, not just at build time, so reruns, backfills, and late-arriving data can't silently create duplicate rows.

→ see it in Cost Analytics 03

CI-gated, AI-assisted

Every pipeline repo ships with lint + a schema validator tested against real broken input: a malformed rule or a broken job dependency fails the build before it fails in production. I use Claude Code across the full git lifecycle, including branching, commits, PR reviews, and merges, to move faster, but every change still ships through a branch, a pull request, and a green CI check before it touches main. AI accelerates the workflow; it doesn't bypass the gate.

→ see it in DQ Framework 04

Documented for the next person

Architecture docs, decision logs, and known-limitations sections ship with every pipeline, not just the happy path. The goal is that someone else can maintain it without asking me first.

Deep Dive · Data Engineering Flagship Project, 2026

Osteoarthritis Market Share Forecasting Pipeline

In plain English: a drug company wanted to know whether its osteoarthritis injection was losing doctor visits. The raw data was scattered across Excel files and 171 public datasets. I built the pipeline that turns all of it into one checked, repeatable database, and that tells you when it cannot be trusted.

Problem

Market data arrived as four nested Excel extracts (72 months, 160 products, 7.19M+ visits) plus 171 public files from CMS, CDC, SEC and FDA (about 24 GB). Nothing was joined, checked or repeatable.

Why

A forecast is only as good as its data. If nobody can trace a number, rebuild it, or tell when it silently changed, nobody can trust the conclusions built on top of it.

How

A re-runnable Bronze to Silver to Gold pipeline into a star schema, a Pandera validation gate, 11 quality checks against a stored baseline, a SHA-256 audit of every extract, a golden regression test, and an eight-stage publish that swaps the finished database in atomically.

The warehouse in one picture

One central table of visits, surrounded by lookup lists. Anyone can slice the numbers by month, product, specialty or patient group without re-cleaning anything.

The safety net: an eight-stage publish

1. Run it twice, get the same answer

An end-to-end test runs the real extracts through every stage twice and fails if anything differs.

2. The system flags old data

Monitoring says so out loud instead of quietly forecasting from old numbers.

3. Joining sources exposed a contradiction

Putting SEC sales filings beside the visit data showed the two disagree, before anyone built a target on the decline.

Business impact: what the engineering buys the business

1
Every number traces back

Every extract is SHA-256 hashed on each run, every prediction row carries its data version, and a golden test compares the rebuilt warehouse with committed values.

2
A bad run cannot damage good data

A failed run names its stage and leaves the last good database untouched, so reports never read from a half-built warehouse.

3
The system says when its data is old

At the last run, monitoring reported the data as 454 days old against a 100-day limit, instead of quietly forecasting from stale numbers.

4
Joining sources surfaced a contradiction early

Company sales rose 5% and 6% while visits fell 14% and 36%. Catching that at the data layer kept a possibly wrong decline out of targets and forecasts.

Status: the pipeline, tests and CI are complete. A Streamlit site over the published warehouse is built but not deployed, and the data ends in July 2025, so the monthly refresh runs on tests and a schedule, not new data. These are engineering outcomes, not measured revenue impact.

This is where principle 02 (idempotent by design) isn't an abstraction: the whole publish is run twice on real data and must produce identical content, and a failed run can never replace the last good database.
